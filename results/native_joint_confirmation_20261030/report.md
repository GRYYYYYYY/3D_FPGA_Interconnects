# 原生 CPU–GPU 联合方案四核确认结果

本轮分析与预声明实验已完成，联合加速目标尚未达到。GEMM 三次同核主比较全部合法，但 batch 三次都比原版并行 VPR 慢。elliptic 的 batch 本次合法完成，但同轮原版崩溃，缺少合格主基线；其 CPD 相对此前相同输入的合法串行参考增加约 20.6%，也不支持启用当前方案。

CPU 算法、调度与 GPU 的收益均可计入联合优化。这里未达标的原因是实际全流程结果，而不是要求 GPU 必须独立胜过我们的 CPU。当前 native_parallel 是集成控制，并没有新增已证明更快的 CPU 算法；原版已有 PartitionTree/TBB 并行路由，单纯启用四线程不算新贡献。

## 实验与比较口径

按 [预声明计划](plan.json)，在同一 H100 80GB 作业、同一节点 `qb-prod-gpu433` 上，比较原版并行 A、native CPU 控制 B、所有权保护 CPU 控制 C、CPU–GPU batch D。全部 VPR 线程及 GPU 服务/驱动线程限制在 `[32,33,34,35]`，对应同一 socket 上四个不同物理核、每核一个逻辑 CPU。平台分配为 10 CPU 配额，但被测进程实际限制为四核；不声称核心独占。每五秒的线程亲和性采样全部通过，GPU 进程最多观察到七个线程，均在相同四核集合内。

GEMM 每组三次，顺序分别为 A/B/C/D、B/C/D/A、C/D/A/B。elliptic 先每组一次，因初筛失败，按预定门槛跳过后两轮。算法源码与参数不变：2048 pops、batch 上限 4、50 μs 等待、64 cooperative blocks、200 路由迭代、900 秒单进程上限。关闭 CUDA events、快照与 CPU 配对回放，保留真实 GPU 提交及错误记录。

所有变体计时前同等预读输入，单独记录预读时间；每次新进程仍重新解析资源图、构建 lookahead、初始化 GPU（如适用）、路由与进程内 FULL/STA。进程时间和包含独立锁定原版 FULL/STA 回读的 workflow 分别报告。编译、输入校验/预读、工作包暂存和归档不混入这些时间。这是输入预热条件下的测量，完整细节见 [实验说明](../../docs/native_joint_confirmation.md)。

中位数之比对应 batch 进程耗时增加约 3.60%、workflow 增加约 2.72%；逐轮配对也全部较慢。三次样本不作统计显著性声明。CPU 控制的进程差异主要包含准备阶段波动，不能据一次更快就宣称 CPU 算法改进。原版和 native CPU 的布线中位数相同；guard 与 batch 的布线阶段均有额外成本。

12 项均零超用、FULL/STA 与独立回验通过。九项 CPU 结果路由主体哈希完全一致，均第 14 轮收敛。batch 分别在第 15/14/15 轮收敛；CPD 全部为 13.2667 ns，原版线长 4,095,331，batch 为 4,093,629 / 4,094,121 / 4,093,801，满足 +5% 质量约束。

batch 三次真实提交 111/101/116 个 GPU 结果，无错误和 fallback。合计 328 个查询、327 个批次，仅一个批次大小为 2，其余大小为 1。CPU 在 GPU 执行期间完成的独立查询分别为 13,887/12,864/13,229，说明重叠确实发生，但没有形成足够多的并发长查询。

GPU 运行时准备三次为 3.594/3.577/3.580 秒，包含模型/图准备与初始化；每次静态逻辑载荷约 3.096 GB。按 batch ID 去重后的全部搜索调用累计仅 0.415/0.356/0.430 秒。这些是主机调用墙钟，**不是纯 kernel 时间**，也不能把可能重叠的 CPU/GPU 累计时间直接相加。GEMM 的全流程重点是 lookahead 与固定准备成本，不能只优化搜索 kernel 后便假定整体会快。

## elliptic：失败类型已经分开，batch 单次合法但不满足启用条件

| 变体 | 进程秒数 | 结果 |
| --- | ---: | --- |
| 原版并行 | 104.481 | SIGSEGV；最后可见第 63 轮、30 个超用节点，未形成合法最终结果 |
| native CPU | 467.785 | SIGKILL；最后可见第 70 轮、26 个超用节点；未达到 900 秒超时，终止原因未定 |
| guard | 151.177 | 正常报告路由失败，200 轮后仍有 1 个超用节点 |
| batch | 182.037 | 第 157 轮零超用；进程内与独立 FULL/STA 通过，workflow 184.429 秒 |

崩溃前最后观测的超用数不是最终拥塞报告。SIGKILL 不直接等同于 OOM、死锁或测试超时；没有系统事件证据支持这些归因。

guard 的 [超用报告](artifacts/run/elliptic_initial/elliptic_0_guard/report_overused_nodes.rpt) 定位到 `CHANY 245362`，L4 线段 `(10,24,1)→(10,27,1)`，容量 1、占用 2。涉及网络 `353 / n_n8389` 和 `2529 / n_n7966`。这说明本轮无 GPU 的保护路径也未收敛，不能把所有拥塞失败归因于 GPU。

batch 提交 7,264 次 GPU 结果，全部是单查询批次，错误/fallback 为零；保护冲突等待 36,433 次、旧树导致保护域扩展 159 次，GPU 执行期间 CPU 完成 125 个独立查询。GPU 搜索主机调用累计 139.694 秒、查询状态整理累计 8.967 秒，运行时准备 0.752 秒。它们用于成本诊断，不能把这些累计项直接当作互斥阶段相加。

本次 batch CPD 为 **13.6102 ns**、线长 98,441。同轮原版和 CPU 对照都没有合法完成，故不存在有效的同轮加速比或相对并行基线质量结论。另经输入五项 SHA256 核对，此前合法串行原版参考为 11.2895 ns、线长 99,232；本次 CPD 增加 **20.56%**，超过 5% 门槛。这是历史质量交叉核验，不计算跨作业时间比，也不替代失败的同轮并行参考。详见 [诊断数据](diagnosis.json)。

## 原版崩溃的离线证据

归档保留了 `core.58431`，196,161,536 字节。使用与作业相同的冻结原版二进制及固定运行库离线读取，栈定位到 `RouteTree::add_subtree_from_heap(...)+602`，调用链经过 `update_from_heap`、`route_sink`、并行分区路由。另一个工作线程同时在 `timing_driven_expand_neighbours` 中。

故障指令为 `mov (%rcx,%rax,4),%r8d`，`rax=0xffffffff`；基址加该索引乘四，恰好等于 core 中的 SIGSEGV 故障地址。这确认了无效边索引被用于回溯读取。未修改的原版源码中，相关循环从共享 `rr_node_route_inf[new_inode].prev_edge` 继续找前驱；源码与锁定提交 `0b912334fdd83bb754b302146ac0d1ec9edc9a0e` 一致。

**无效前驱的上游来源尚未确认。** 并发写入干扰是待验证假设，不是仅凭这个 core 就证明的数据竞争。二进制有函数符号但无 DWARF 行号，worker 系统库未完整保存，系统栈帧解析有限；VPR 函数与故障指令来自准确匹配的二进制。证据见 [崩溃分析](crash_analysis.json)、[堆栈](diagnostic_core/backtrace.log)、[寄存器](diagnostic_core/fault_registers.log)。调试器和依赖只解包到本轮目录，软件包按官方软件源 SHA256 校验，没有改系统安装。

## 优化及接管决策

当前保持原有 CPU 默认，保留所有权保护；本轮不启用固定 2048-pop batch 为默认方案。下一轮按以下顺序推进：

1. **elliptic 先定位并行前驱状态与质量问题。** 在独立诊断构建中记录无效/循环前驱、网络与 sink、分区、前驱写入线程及版本；补充进程峰值内存与 cgroup memory events，区分 SIGKILL 来源。围绕 guard 的两个冲突网络检查保留树、拆线及占用变化，再验证修复后的合法收敛和 CPD。仅增加迭代或删除保护不能替代这一步。
2. **GEMM 优先拆 lookahead 内部成本。** 继续分解 wire lookahead、SOURCE/OPIN 映射及距离成本表，确定 CPU 并行、数据结构优化或批量 GPU 预计算的具体对象。任何缓存/复用必须同等提供给原版基线，并报告首次构建和摊销条件。
3. **以真实状态验证 GPU 与调度改动。** 复用此前已验证的 H3DTAK2 完整快照，检查 kernel 扫描/扩展/同步与受保护的细粒度任务释放。此前诊断发现的父分区释放约束是下一步检查对象；本轮批次计数本身不能证明所有长查询天然不可并行。新接管规则使用上线可取得的特征，并在独立留出网络/迭代及完整同核流程中确认联合收益。

仍按 `T_joint < T_original_parallel` 加合法性、质量门槛验收；GPU 是否进一步优于我们的改进 CPU 用于归因和选型，不作为额外硬门槛。此前完整状态与 kernel 诊断见 [上一轮报告](../native_diagnostics_20261029/report.md)，不能把旧计时与本轮拼接成加速比。

## 验证、失败与保存

- 16 项测量全部保留，13 项成功的路由哈希和独立 FULL/STA 已核验；345 条 GPU 回放 oracle 路径通过，153 个冻结文件校验通过。实际 CUDA 库 SHA256 为 `a928e2c8a65f470e293ee3147189b9814d1c62a38902eb150b42063cb3ae36a5`。CPU 二进制与路由算法源码保持冻结版本。
- 本机四核选择测试 3 项、报告门槛/失败分类测试 9 项、镜像配额错误回归测试 2 项通过；ex5p 三个 CPU 控制的本机 smoke 均通过 FULL/STA 与亲和性检查。最终分析还执行了 [证据核验脚本](verify_evidence.py)，见 [核验结果](evidence_verification.json)。
- 首次作业因项目存储配额导致镜像异常退出，零完整性能测量；失败回执保留。修复后作业又记录了 19 次镜像写入配额错误，但求解未被中断，完整归档正常生成。因此最终结论来自校验后的归档，而非 live 镜像。归档预留初始 1024 MiB，后扩为 2300 MiB，扩容记录单独保存。
- 最终归档 1,830,369,386 字节，SHA256 `ba4197c7ad0ef35f55e4d237ac6b6ffa782fcf6716e9f6e0509df1deecb2d0d8`。已结束的生成归档及既存旧 core 经逐文件 SHA256 校验后移至 `results/native_archive_store_20261030/`，原项目路径以软链接保留，相邻源码工程未改动。未来 GPU worker 重放需重新暂存这些 global_user 归档。见 [全部迁移记录](../native_archive_store_20261030/relocations.json)、[旧 core 保存记录](../native_archive_store_20261030/preserved_legacy_core/relocation.json)、[本次归档迁移](final_archive_relocation.json)。

# 并行状态修复与 GEMM lookahead 优化结果

本轮按用户指定顺序完成：定位并修复两处并行分区状态更新缺陷，恢复 elliptic 质量，再实现并验证 GEMM lookahead 并行化。最终同一 H100 节点、相同四物理核的三轮比较中，GEMM 联合方案均比原版四线程更快，达到本电路的联合收益门槛。该结论不要求 GPU 单独胜过改进 CPU。

## GEMM：三轮完整流程收益成立

平台分配10核配额，全部被测求解及 GPU 服务线程统一固定在四个物理核 `[48,49,50,51]`，每核仅一个逻辑 CPU，联合方案额外使用一张 H100。原版仍使用其已有的 parallel 路由器与四个 workers；新 lookahead 只在候选开启。所有输入同等预读，每次重新构建 lookahead，无缓存复用。核集合受约束，不声称节点或物理核独占。

`workflow` 含工作目录准备、路由哈希和统一原版独立回验；进程时间包含 VPR 自身加载、lookahead、GPU 准备、布线与进程内检查。编译和输入预读单独记录。这些不是 GPU kernel 时间，也不是文件系统冷缓存实验。

## 收益来源与实际选型

| GEMM 阶段中位数，秒 | 原版四线程 | 联合 batch | 改进 CPU，单次 |
| --- | ---: | ---: | ---: |
| 资源图加载 | 53.33 | 52.72 | 52.09 |
| lookahead 构建 | 170.02 | 41.67 | 41.07 |
| Routing | 36.50 | 46.33 | 37.89 |

lookahead 约 **4.08×** 加速，节省约 128 秒，是完整流程收益的主要来源。GPU 准备计数中位数约 4.25 秒；它与 VPR 阶段计时不能直接相加。Routing 在联合方案中更慢，单次改进 CPU 也比三个 batch 样本都快。因此本轮已证明联合方案优于原版四线程，**尚未证明 GPU 相对改进 CPU 的额外提速**；CPU 单次控制仅用于归因，不替代重复性能确认。

新增的是 lookahead 独立采样的并行化，不把原版已有的四线程网络路由算作新贡献。使用独立搜索状态和采样代价表，按原采样顺序合并，保留相同 delay 时第一个 congestion。ex5p/GEMM 串并行 wire map 逐字节相同、路由主体相同；GEMM wire map SHA256 为 `458b7439c7fb2bd2ffae133d2d5cb89e3d3428c8893f83afc3aa4a8cc7501e8e`，本机与首轮 H100 诊断也一致。

`VPR_HYBRID_LOOKAHEAD_PARALLEL=1` 或实验脚本 `--parallel-lookahead` 显式开启新采样并行。默认仍关闭；GPU 仍需显式配置。接管预算 2048、batch 上限 4、等待 50µs、cooperative blocks 64、CUDA kernel 和所有权保护范围均未调整。

## elliptic：质量恢复，未声明加速

实时标签审计捕获网络 1120/1473 同时写 RR207790。第一处根因是动态扩框输出列表按值传递，分区树收不到更新；仅修这一处后，第 51 轮检查又发现拥塞模式全量重载搜索框漏通知。修复为引用输出，并在两类框更新都完成后统一更新分区归属；全量重载通知所有网络。增加分区包含检查、可关闭的标签审计，以及回溯无效边与循环链检查。

三次 batch 均独立 FULL/STA 通过，质量满足同轮串行参考 +5% 门槛，合计真实提交 24,679 次，零错误/fallback。仅 3 个批次包含两个查询，其余单查询；所有权冲突等待计数为零。质量恢复得到重复验证，但 batch 比本轮 CPU guard 慢。由于原版并行历史崩溃，此处串行只作质量参考，不计算相对原版并行的加速比。

## 后续优化方向

优先将改进 CPU 纳入重复与多电路验证，确定新 lookahead 的收益范围及默认启用条件；保留当前 GEMM 联合收益作为已验证结果。GPU 下一步围绕准备成本、真实接管状态回放和独立长查询的可用性优化，并以同核完整流程重新验收。elliptic 继续采用修复后的 CPU 作为速度对照，不因质量改善而默认启用更慢的 batch。

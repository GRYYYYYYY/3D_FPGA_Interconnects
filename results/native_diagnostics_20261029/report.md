# 原生 CPU–GPU 接管诊断结果

2026-10-29。分项计时、真实状态捕获及组批诊断已完成 elliptic/GEMM 验证。**默认保留原生 CPU；本轮没有证明端到端 GPU 加速，不启用新的自动接管规则。** 搜索 kernel 是当前接管通路的主要耗时，原生分区任务发布限制了可组批工作。

机器可读结果：[acceptance.json](acceptance.json)。详细数据：[主诊断](main_diagnostics.json)、[H3DTAK2 捕获与回放](capture_v2_diagnostics.json)、[实现与计时说明](../../docs/native_diagnostics.md)。所有结果均为诊断，不作为生产性能确认。

## 分项计时与选择

主诊断作业 `203702` 在同一 H100 工作节点依次运行原 VPR、pair、batch。pair 保留 CPU 路径并交替 CPU/GPU 测量顺序。以下只统计**未额外捕获/CPU 重复**的配对样本；CPU 列是该接管点之后的真实原生续跑时间，单位秒。

| 案例 | 查询数 | CPU 剩余搜索累计 | GPU 搜索 kernel 累计 | GPU 完整交接累计 | GPU 交接更快的查询 |
| --- | ---: | ---: | ---: | ---: | ---: |
| elliptic | 9,040 | 122.851 | 183.044 | 193.563 | 526 |
| GEMM | 108 | 0.230372 | 0.408514 | 0.687763 | 1 |

“完整交接”从在线 dispatch 扣除单列的初始化、捕获和诊断重复；包括原生状态整理、状态更新、GPU execute、路径/前缀/代价验证及标签提交。其后原生树插入、占用更新和标签清理另列在 commits CSV；整网时延与 STA 留在 VPR 路由阶段，未冒充逐查询时间。

全部 pair 查询（含捕获）中：

| 案例 | GPU execute 主机秒 | 搜索 kernel event 秒 | kernel/execute | 三段复制 event 秒之和 | 原生状态整理秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| elliptic | 184.466608 | 183.177599 | 99.30% | 0.867231 | 6.759865 |
| GEMM | 0.551786 | 0.530703 | 96.18% | 0.021192 | 0.151966 |

主机等待与设备执行重叠，不能再相加。普通主机缓冲区的复制 events 也不是硬件总线测量。每批有唯一 ID，批次时间仅累计一次。即使理想化消除复制，两案例的 kernel 累计仍大于 CPU 剩余搜索，故不优先投入 pinned/异步复制流水，也不把显式同步等待当作额外的纯同步瓶颈。

后续应使用已验证快照分析 kernel 内部的活跃前沿扫描、重复扩展和跨 block 同步，测清哪项主导后再改实现；当前 events 尚不能区分这些内部原因。GEMM 原版资源图加载 43.29 秒、lookahead 构建 143.55 秒、路由阶段 67.73 秒；若另做 lookahead 复用，基线必须获得相同复用条件。

## 真实接管状态与回放

修正版作业 `211643` 采用固定的每 16 个合格接管点采样一次，先选样本再观察胜负，最多 1,024 个。捕获完整原生标签/前驱、堆顺序（含过期项）、树根与树节点、占用/历史、待应用增量、代价参数与边界。CPU 直接恢复原生搜索续跑，未另写替代 CPU 算法。

| 案例 | 完整快照 | 覆盖网络 | 迭代范围 | 原生 CPU 重复 | GPU 校验路径（预热+3次） | 在线 GPU 胜出 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| elliptic | 567 | 168 | 6–189 | 1,701 | 2,268 | 29 |
| GEMM | 9 | 9 | 2–8 | 27 | 36 | 0 |

全部 1,728 次 CPU 重复的路径与代价相同，且与随后实际 CPU 续跑一致；2,304 条 GPU 回放路径均通过原生前缀、后缀连通性、边界、目标与浮点代价校验。两案例最终 CPU 路径正文与主诊断的原 VPR 完全一致，独立 FULL/STA 均通过，CPD/线长分别为 elliptic 11.2895 ns/99,232、GEMM 13.2667 ns/4,092,250；错误和 fallback 均为零。

离线 GPU 每次从原始标签和堆重建输入，预热单列。每状态三次取中位数再累计：elliptic 原生 CPU 7.349558 秒、GPU 完整回放 11.495883 秒（kernel 10.917616 秒），36/567 个中位数胜出；GEMM 为 0.012790/0.051729 秒，0/9 胜出。离线主机实现和在线 VPR 不同，捕获还会温热 CPU 缓存，所以这些数据用于重复性与瓶颈判断，不能直接拟合生产调度收益。离线 36 次胜出与在线 29 次胜出也不能混为同一口径。

早期 H3DTAK1 使用 `RouteTreeNode::all_nodes()` 漏掉树根，在只有 SOURCE 的树上导出了空树；严格回放拒绝了主诊断及稀疏补测。已改为 `RouteTree::all_nodes()`，升级 H3DTAK2，补全原生参数，要求恰有一个根并重新捕获。没有补造旧数据或放宽校验。旧失败、有效在线计时与部分回放记录均保留。v2 明确拒绝旧格式；本机六种损坏状态均被拒绝。

## 组批原因及合法性

batch 使用原生四 CPU 工作线程、GPU 服务线程、2048-pop 接管阈值、最大批次 4、窗口 50 µs、单查询 64 cooperative blocks。所有权范围和同树连接顺序未修改。

| 案例 | 批次数 | 批次大小 | 父分区尚未释放子分区 | dispatch 时有保护等待者 | 其他搜索尚未就绪 | 分区任务排队 | 证据不足 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| elliptic | 7,872 | 全为 1 | 7,693（97.73%） | 160 | 3 | 0 | 16 |
| GEMM | 118 | 全为 1 | 64 | 0 | 38 | 6 | 13 |

证据类别可重叠，原子计数为并发观察；准确的服务队列深度在每次 dispatch 均为 1。elliptic 全程有 47,424 次所有权等待事件，GEMM 有 8 次；事件总数与 dispatch 时等待者存在次数不是同一统计。没有观察到“仅因本请求扩大旧树保护范围才新增”的冲突，不表示所有保守保护均无影响。

elliptic 的主要限制是长查询发生时子分区尚未发布，增加几十微秒组批窗口没有证据能制造更多独立查询。后续可研究受现有保护约束的更细任务发布；当前观察不能证明长查询天然不能并行，更不能据此删除资源锁。

| 案例/变体 | VPR 进程秒 | 含独立回验 workflow 秒 | 结果 |
| --- | ---: | ---: | --- |
| elliptic 原 VPR | 149.849 | 152.242 | 合法、FULL/STA |
| elliptic pair | 351.339 | 353.824 | 同原版 CPU 路径、FULL/STA |
| elliptic batch | 200.127 | 无有效成功 workflow | 200 轮后仍有 5 个超用节点 |
| GEMM 原 VPR | 349.626 | 501.989 | 合法、FULL/STA |
| GEMM pair | 363.184 | 515.430 | 同原版 CPU 路径、FULL/STA |
| GEMM batch | 318.183 | 472.605 | 合法、FULL/STA；CPD 不变，线长 +0.0379% |

elliptic batch 的 7,872 次 GPU 提交虽无局部错误，完整路由仍未收敛，不能计算有效加速比。GEMM batch 进程较短，但包含四 CPU 工作线程，本轮缺少同条件四线程纯 CPU/guard 对照，不能归因为 GPU；也不能用不同作业的控制计时拼出加速。

## 策略、验证与可追溯性

保留 CPU 默认；2048 阈值、64 blocks 均仍是实验参数。优先研究 kernel 内部与受保护的任务发布，不盲扫已有 block 参数或提高阈值。存在获胜查询，但尚无通过独立留出验证的在线规则；“CPU 未来剩余耗时”不能用作在线特征。下一版候选须补同节点纯 CPU/guard 对照、零超用、CPD/线长不超过原版 +5%、独立 FULL/STA 及端到端重复确认。

本机原生构建、8 项既有报告测试、3 项 scaling 测试、8 项新诊断报告测试通过；真实 ex5p 捕获控制路径一致，6 类损坏快照被拒绝。H100 上 345 条旧接口 oracle 路径及 16 条小规模真实接管路径额外通过。详细记录见 [local_validation.json](local_validation.json)。

本轮五个 GPU 作业均已有终态：[job_registry.json](job_registry.json)。主诊断完成六项路由后因 v1 快照回放失败；另有缺失挂载、字节码缓存校验和稀疏 v1 回放失败。最终 v2 作业成功。未覆盖前轮 25 作业登记或旧验收报告。

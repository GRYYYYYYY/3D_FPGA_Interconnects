# 原生 CPU–GPU 联合优化目标（2026-10-30 澄清）

主目标是：在路由合法、零超用、独立 FULL/STA 通过，且关键路径和线长退化各不超过 5% 的条件下，使我们的 CPU–GPU 联合方案端到端优于明确配置的原 VPR。CPU 算法、数据结构、并行调度、任务划分和 GPU 搜索及协作的收益都属于联合方案的有效收益。

理想结果为 `T_joint < T_improved_cpu < T_original`：先证明 CPU 侧改进，再证明 GPU 带来额外收益。可接受目标为 `T_joint < T_original`；GPU 相对我们改进后的 CPU 必须进一步加速，不是联合方案有效性的必要条件。仍应如实报告纯 CPU 与联合方案的比较，帮助选择实际最优配置。

此前“四线程 CPU 贡献尚未隔离，所以不能把 batch 作为 GPU 加速证据”应限定为：暂不能归因到 GPU 的独立增益。它不能用来否定联合方案相对原 VPR 的整体收益，也不应把研究限制成只优化 GPU kernel。

## 已有 GEMM 结果的正确解释

主诊断作业内，原 VPR 单线程进程为 349.626 秒，四 CPU 工作线程加 GPU 的 batch 为 318.183 秒，观测时间短约 8.99%；含统一独立回验的 workflow 为 501.989 与 472.605 秒，观测时间短约 5.85%。batch 实际提交了 118 次 GPU 结果，FULL/STA 通过，CPD 不变、线长增加约 0.0379%。

这是一条值得确认的联合优化线索。尚不能宣布稳定收益的原因是只有一次诊断配置测量，尚缺关闭诊断后的重复端到端确认；并非必须先证明 GPU 独立贡献。旧计时、失败和验收记录保持原样，本次只澄清目标和解释。

继续明确区分原 VPR 单线程与四线程基线。相对单线程的收益应标明线程数；同时给出同四 CPU 配置的原 VPR 对照，说明资源增加和算法变化的作用。不要把相对单线程的收益写成已经胜过原版四线程，也不要要求每一项局部改动或每个 GPU 查询都单独获胜。

## 调整后的执行顺序

1. 优先做 GEMM 联合方案的正式候选确认：关闭 CUDA 诊断 events、捕获及 CPU 重复回放，同节点固定输入，对原 VPR 和联合方案至少做三次完整流程比较，报告所有重复的进程与统一回验 workflow 时间及质量。
2. 同轮包含原 VPR 四线程、我们的 CPU/guard 控制，用于归因和选型。以联合方案相对明确原 VPR 基线的完整收益验收；CPU/GPU 贡献拆分不另设 GPU 独立获胜门槛。
3. 按全流程成本选择优化位置。CPU 调度、受保护的任务发布、数据处理及 lookahead 与 GPU kernel 均在范围内；GPU 内部诊断是其中一项。任何预处理或缓存策略都要明确冷启动成本、复用条件及摊销方式。
4. elliptic 先解决 batch 的完整路由收敛问题，再计算有效收益；其快照仍可用于 kernel 优化。保留所有权保护，避免局部搜索通过而完整路由不合法。

没有足够数据证明 CPU 算法已经优于原版；这正是 CPU 对照要回答的问题。当前保留 CPU 默认是部署状态，不是研究目标收缩。

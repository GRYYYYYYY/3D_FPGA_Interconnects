# 原生 lookahead 方法差异与优化可行性分析

本轮于 2026 年 11 月 1 日完成定向查新、源码依赖分析、历史诊断重算和独立语义验证。当前 CPU 采样并行的性能证据仍有效，但采样模型、Dijkstra、确定性并行和有界 pipeline 均有先例，不能笼统称为新算法。本次新增的具体发现是：当前 map 插值在不同二维切片之间没有数值依赖；此前维护全部组的全局顺序是保守实现约束，可以研究消除重复扫描和提前释放中间结果。

独立验证使用从当前源码直接提取的插值函数，并不运行完整 VPR。它支持方法推理，尚未产生新版本的原生 GEMM/elliptic 加速结果。现有 solver 源码、默认选项和冻结实验均未修改。

## 插值实际依赖与重复工作

全局表索引为 `F[from_layer][to_layer][channel][segment][x][y]`。`fill_in_missing_lookahead_entries()` 遍历所有层，但两个邻居查询函数始终保持前四个索引不变，只改变 `x,y`。因此：

1. 不同 `(from_layer,to_layer,channel,segment)` 的二维切片没有插值数值依赖。
2. 同一切片内，缺失项会读取之前已填入的邻居；必须保留原有 x 外层、y 内层的扫描顺序及浮点求和顺序。
3. 每个组的 `set_lookahead_map_costs()` 覆盖该起始层的全部目标层/坐标，包括无效项。因此此前给尚未采样的切片填入的临时默认值会被完整覆盖。
4. 一次完成填充后，重复填充不再改写该切片。对尚未写入的层，最终仍需补齐原流程产生的默认值；完全未处理的 segment/channel 则应保持未处理状态。

在组键唯一、完整覆盖各组原始结果且没有中途消费者的当前调用路径下，两种等价重排成立：先写完原始结果、每个使用过的 segment/channel 最后填一次；或各组完成后只填自己的起始层切片，最终补齐从未写入的层。后一种形式允许组结果提交后立即释放，无需等全部组完成。

这纠正了旧文档中“插值遍历多层，因此必须保持全部组全局顺序”的推断。遍历范围不等于数据依赖；原实现保序是安全的，但不是唯一安全方案。

设 L 为层数、K 为实际使用的线型/方向组合数、A=W×H；若每层都有这些组，旧代码的缺失项检查次数为 `K L³ A`，每个组合填一次为 `K L² A`。这是删除冗余扫描的工作量关系，不是整个 lookahead 或进程的 L 倍加速；主要 flood 成本并没有因此减少。

[分析脚本](../scripts/analyze_native_lookahead_semantics.py) 从原生文件提取三个完整插值函数、`Cost_Entry`，并使用原生 `NdMatrix`、`nint`、不可达哨兵与有效邻居阈值。测试驱动只提供网格和原始表，不重写插值算法。编译命令、源码绑定和结果保存在 [分析结果目录](../results/native_lookahead_analysis_20261101)。

| 检查 | 结果 | 适用范围 |

## 重复搜索能否直接合并

不能把不同起点压成每个 RR 节点的一个最近来源。例：起点 x=0 和 x=5 到同一 x=6 的 IPIN，代价分别为1和2；原采样需要相对距离6的代价1，以及相对距离1的代价2。只保留最近来源就丢掉后一个桶。[可执行反例](../results/native_lookahead_analysis_20261101/reduction_checks.json) 验证了这个差异。

当前 wire flood 使用 `rr_indexed_data.T_linear` 累加延迟，没有实现完整上游 RC 递推。因此此反例基于来源相关坐标即可成立，不需要借用当前代码未执行的 RC 机制。不同起点搜索空间有重叠，并不能证明其标签可以合并。

完全相同 RRNodeId、图/代价状态、搜索限制和记录坐标规则下的重复 flood 可以作为精确复用候选；相同节点也必须确认完整上下文一致。现有日志只记录采样数量，没有记录所有起点 ID，故尚不能量化真实可去重比例。下一步诊断先记录身份与重复率；若无重复就关闭此分支。跨起点共享邻接遍历需要保留来源标签，可能增加工作区和同步成本，不能预先承诺收益。

## 已有成本证据与内存约束

重新汇总同一份 GEMM 串行诊断：初始化0.240893秒，搜索累计160.782565秒，初始化占二者之和约0.150%。另一份组内并行诊断中，归并墙钟累计0.066193秒、组墙钟累计43.126509秒，约0.153%。两份诊断不跨运行相除；并行 search/init 是线程累计量，不能从墙钟时间直接扣除。详见 [分项汇总](../results/native_lookahead_analysis_20261101/profiles.json)。仅优化清零或归并，按这些已测区间看，难以解释显著的完整流程增益。

现有全局 pipeline 对全部 G 组预分配结果表；最多2P个 token 只限制在途样本结果，不限制这 G 个组表。设一张样本表有 M=LWH 个单元，工作区数为 Q，则当前中间结果存储近似为 `G M + 2P M` 个单元，另加 Q 份搜索标签/堆，以及始终存在的最终全局表。不能把 token 有界等同于整个算法内存有界。

本机 ABI 中 `Cost_Entry` 为12字节，每个 `std::vector<Cost_Entry>` 头为24字节；SMALLEST 模式每个有效单元还独立存储一个条目，并承担分配器开销。仅针对 SMALLEST 的连续标量表有明确的存储减少空间；若加入样本序号，需重新计入空间。它属于可验证的表示改进，不自动成为论文创新。不能把表大小减少比例写成进程 RSS 减少比例，RR 图和搜索工作区可能占主导。

有界活跃组候选应在执行前按内存预算、单表大小和工作区高水位限制组数；每组提交后释放结果。若仍使用 TLS，还需记录实际分配过的工作区数量，不能仅凭并发上限断言全程只分配 P 份。

历史同二进制归因三元组进一步拆出如下残差：

| 变体 | 进程秒 | 已有顶层计时之外的残差秒 |
| --- | ---: | ---: |
| 旧组内实现 | 233.235 | 41.825 |
| 重构后的组内控制 | 246.583 | 53.713 |
| 同一重构二进制开启 pipeline | 244.159 | 53.189 |

重构控制相对旧实现的13.348秒增加中，约11.888秒位于这些既有计时区间之外。此处排除嵌套计时与重叠的 STA 汇总，计算见 [残差分析](../results/native_lookahead_analysis_20261101/attribution.json)。它仍只是一次历史三元组，无法定位到分配器、序列化或清理函数，也不能排除宿主波动；需要在这些未覆盖边界增加计时。

## 后续实验取舍

优先研究“消除伪依赖、按切片提交、限制中间结果存储”。这一方向有源码推理和语义证据，仍需先量化成本上界。首次原生实验只做最小插值调用重排，再分别隔离连续标量表与调度的影响，避免又一次同时重构多处导致无法归因。

不优先做 visited epoch、无来源标签的多源合并，或继续盲调 pipeline token。完整流程残差和实际 flood 重复率先由诊断解决。正式性能与诊断分开，GEMM/elliptic 在同物理核预算下测4/8核、三次配对；双方共同缓存的对照继续保留。质量/合法性失败不计算加速。具体阶段、对照和门槛已记录在 [下一轮实验规格](../results/native_lookahead_analysis_20261101/next_experiment.json)。

当前可成立的表述是“原生 map lookahead 的等价并行实现及资源效率研究”。若后续方法同时给出明确依赖分解、减少的扫描/存储、内存预算下的扩展性和稳定完整流程收益，可据此评估论文贡献；本轮没有证明其文献首创性，也没有以合成测试替代原生加速结果。

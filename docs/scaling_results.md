# 同节点 VPR–GPU 规模实验，2026-10-25

本轮六个真实电路没有出现当前 CUDA 实现反超原 VPR 的交叉点。扩大电路规模后，
全图状态处理和搜索工作量增长，另有拥塞协商不收敛的问题。此前相对旧 CUDA 的 16.86×、
相对四线程原型 CPU 的 7.91× 加速仍成立，但不能外推为相对 VPR 的优势。

时序代理与源点构树对照改善了两个小案例的关键路径，却增加了线长，在其他案例失败或超时。
因此尚未达到“轻微质量退化换取稳定端到端加速”的研究目标，也不能据此断言其他 GPU 算法没有交叉点。

同一工作节点顺序运行，原 VPR 使用一个 CPU worker，GPU 使用一个主机路由线程。
每个案例内架构、布局、RRG、通道宽度和容量相同。三个方法各运行首轮，成功后再重复两次；
失败首轮保留，确认轮明确标记未尝试。每轮轮换方法顺序，路由上限 200 轮、600 秒。

54 个计划记录中，实际尝试 40 次：33 次完整合法、4 次拥塞失败、3 次超时；14 次未尝试。
原 VPR 为 18/18 成功，默认 GPU 为 9/12，时序代理 GPU 为 6/10。
这是按首轮结果决定是否重复的实验计数，不是独立随机样本的成功概率估计。

## 时序改进对照

`delay_proxy` 使用 `1 + round(switch Tdel / 1 ps)` 边权，并以原始源点距离构建最短路树；
默认 `unit` 的增量构树保持不变。这是边权与构树策略的组合对照，没有独立分离两者贡献。

| 电路 | 默认 GPU CPD ns | 时序代理 CPD ns | 相对 VPR CPD | 相对 VPR 线长 | 时序代理完整流程 s |
|---|---:|---:|---:|---:|---:|
| ex5p | 7.80663 | 6.61819 | +17.89% | +49.66% | 13.606 |
| softmax | 10.4208 | 9.56397 | +25.19% | +45.91% | 51.085 |

clstm 在 200 轮后剩余 1 单位超用；elliptic 剩余 99；reduction 和 gemm 均在 600 秒超时。
本配置没有 STA 关键度反馈，没有 RC 时序优化，也没有重新校准改变边权尺度后的拥塞权重。
因此它只证明这一具体配置的取舍，不能代表时序驱动 GPU 方法的最佳质量。未将它设为默认。

## 工作量和失败分析

1. **搜索范围过大。** 当前 CUDA 等待所有可达节点的距离收敛，CPU 依次发起网络构树。
   softmax 的原 VPR 搜索约 0.489 秒，默认 GPU 搜索中位数约 17.825 秒。
   原 VPR 首轮约 63.6 万次 heap pop，而 GPU 有约 87.3 亿次前沿顶点访问。
   两种计数不是等价操作，不能直接当作指令或加速比，但反映搜索工作量的巨大差异。
2. **全图状态处理随规模增长。** 每棵树及修复重试都会上传完整 occupancy/history/allow、
   重置节点状态并重算全部边代价。clstm 默认 GPU 首轮累计 H2D 约 582 GB。
   gemm 默认 GPU 最后打印到首轮 12,288/206,155 条网络时，累计 H2D 已约 1.274 TB，
   前沿访问约 1,421.6 亿。计数包含初始静态图上传，主要增长来自反复状态上传。
   [中途计数 CSV](../results/h3d-vpr-scale-20261025-140823/partial_progress.csv) 是最后已打印进度，不能冒充最终计数或完整解。
3. **拥塞协商停滞和数值饱和。** clstm 默认方案从第 14 轮起就停在 2 单位超用，
   定位到两个普通 CHANY 资源，不是跨层资源不可达；原 VPR 已给出合法解。
   `present` 每轮增长，在约第 46 轮接近上限，代价饱和会与不可达标记合并。
   elliptic 第 45→46 轮超用由 109→714，并出现 6 条未连通网络，与这种限制一致。
   但 clstm 更早停滞，不能把全部收敛失败归因于饱和；仍需受控消融。
4. **主机和回验开销不可忽略。** reduction 首轮 GPU 路由进程约 494.27 秒，
   审计 42.98 秒、导出 56.84 秒、原 VPR 回验 55.82 秒，总流程约 650.48 秒。
   主机批次生成还会反复遍历剩余网络，代码复杂度约为网络数平方除以批大小；
   这项尚无独立 profiler 归因，不能声称它占了某个已测比例。

据此，下一轮应先减少与目标无关的搜索，采用有正确停止条件的目标导向/优先级搜索，
并验证独立最短路 oracle；再把节点状态常驻设备、只更新变化项，消除每棵树的全图处理和
主机反复扫描。质量方面应接入 VPR 的时序关键度及拥塞尺度，并区分有限高代价与不可达标记。
这些修改后再复用同一套冻结案例测交叉点，继续单纯加大电路不能验证算法已改善。

## 验证与边界

实际 H100 的 CTest 3/3 通过，包含增量多源搜索 oracle 和新增源点多终端树校验；
本机 CPU CTest 2/2、Python 测试 6/6 通过。所有合法 GPU 结果经过独立图审计和原 VPR FULL/STA。
最终 [完整性核验](../results/h3d-vpr-scale-20261025-140823/integrity.json) 独立检查源码快照、
路由 JSON 指纹、33 份成功 FULL/STA 日志和全部 36 个配对比较；平台终态为 `job_succeeded`。
当前实验未改 HLS，也没有新增 FPGA 上板性能结论。

端点仍由冻结的参考 VPR route 提取，不使用其内部路径；图转换和端点准备是独立离线步骤，
本轮线上时间未包含这些步骤。首次 gemm 准备耗时约 810 秒。因此“完整流程”的严格范围是
固定端点路由至 FULL/STA，尚不是从原始电路开始、独立替代完整 CAD 工具链的端到端时间。
计时前校验输入哈希，本轮不是冷文件缓存实验。三次重复使用相同布局，不能替代多种子泛化实验。

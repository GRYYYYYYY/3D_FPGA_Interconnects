# 统一调度 lookahead 采样的实验实现

实现位于 `vendor/vtr_cpu_tasks`，来源和补丁冻结在 `results/native_cpu_paper_20261031/tasks_provenance.json` 与 `tasks_changes.patch`。这是 CPU 实验候选，开关 `VPR_HYBRID_LOOKAHEAD_TASKS=1` 默认关闭，没有 GPU 依赖。主矩阵仍使用先前冻结的 `vtr_cpu_paper` 二进制。

## 调度问题

原有优化逐一处理 `(起始层, 线段类型, 通道方向)`，每组内部通常有四个 Dijkstra 采样；一组结束后才开始下一组。在本轮双层 ex5p 诊断中实际为10组、40个采样。因此组内并行不能充分利用八核，也不能用后续组的工作填补当前组的不均衡。

直接并行最外层循环会带来另一个问题：`fill_in_missing_lookahead_entries` 会遍历并写入多个起始层，原调用作用域会与其他组的写入冲突。本候选采用全局保序来避免该冲突。2026-11-01 的进一步分析确认，各二维切片的插值没有跨切片数值依赖；通过缩小写入范围及补齐未采样层，可以研究更弱的同步约束，见[方法差异与语义验证](native_lookahead_novelty_analysis.md)。此外，代价相同的样本会保留先出现样本的拥塞代价；只做无序最小延迟归约可能改变模型。

## 实现与等价性边界

1. 按原来的层、线段、方向、采样顺序生成任务。样本选择和异常类型的穷举回退没有改变。
2. TBB pipeline 跨组调度单次 flood。每个工作线程拥有独立的标签数组与优先队列，资源图只读；每次 flood 仍完整重置标签。
3. 最多允许 `2 × P` 个样本结果在途，P 来自 VPR 已设置的 TBB 并行预算。使用每线程工作区并跨组复用，避免每组重新建立一批工作区。
4. 输出阶段严格按输入顺序归并各样本。相同延迟仍保留原来先出现的拥塞代价。
5. 所有独立采样完成后，按原有组顺序执行全局 map 写入和缺失项插值，避免原插值调用遍历全部层所产生的写入冲突。这是本候选的保守实现选择，不是必须维持的跨层数值依赖。

对于具有有限有效代价的采样路径，每个样本内部的 Dijkstra 操作与原实现相同；按原序合并各样本的最小条目，与直接按原序处理全部条目一致。不可达位置保留原有空条目语义。全局插值的输入及执行顺序也保持一致。这个推理不能替代实际检查：测试对每个核数、每个变体写出的 map 做原版串行字节级对照，并要求原生与独立 FULL/STA、零超用以及质量检查通过。

若 G 为组数、M 为单个采样 map 的大小、V 为搜索标签空间，则主要额外存储包括 `G × M` 个组结果、最多 `2P × M` 个在途结果和约 `P × V` 的搜索工作区。共享资源图另计；实际峰值内存仍以进程记录为准。当前实现未声称适用于任意层数；验证覆盖原有双层 Hecate 和新增单层 Hecate。

## 验证与计时

二维和三维 ex5p 的18项预检覆盖1、4、8核、串行重构控制、原有组内并行和新 pipeline。全部 map 与原版串行逐字节一致，全部路由合法且质量一致。四核诊断记录为10组、40次 flood、8个在途 token 上限和4个实际工作区。GEMM 的4/8核三次配对确认及1/2核补充由 `tasks_plan.json` 执行，16/16项合法并通过 map 字节检查。

该候选研究中的所有计时变体都在进程内写出 map，因此序列化成本是对称的。不能把此研究的时间直接与另一 CPU 核组的主矩阵时间相除；额外收益必须使用本研究中相同核组、核数、输入和重复编号的配对。profiling 仅用于缓存资格检查，正式计时关闭。

这是可验证的调度与资源管理候选，不自动证明性能优势或论文新颖性。即使重建 lookahead 更快，也不代表共同缓存条件下的路由搜索被加速；两个问题分别报告。

## 候选的完整结果与取舍

相对原有组内采样实现，GEMM四核三次进程速度比中位数为0.937×（范围0.932–0.942），全部变慢。八核lookahead阶段中位快1.924×，但完整进程仅1.010×（0.998–1.015），含独立回验workflow为0.996×。单核/双核各一次探索的进程速度比分别0.987×/0.943×，不作为统计确认。

另外五电路的30项扩展全部合法且map字节一致，但性能不一致：四核ex5p中位1.222×，reduction为0.981×；softmax和CLSTM存在明显重复波动。当前不据此设定按电路选择最佳实现的自动规则。

四核GEMM同二进制归因三元组为：旧实现233.235秒、重构后仍用组内调度246.583秒、重构后启用pipeline244.159秒；lookahead分别40.58/40.20/39.88秒。后两项使用相同二进制SHA。重构后保留旧调度就出现了额外成本，所以不能把候选版本的整个退步都归因于跨组调度。三元组只有一次，是定位线索，未证明分配器或具体函数为根因。

两套构建的523条编译/链接命令在替换目录路径后相同。1421个实际项目源码/生成依赖配对核对，除预期三个源码文件外，差异只有生成文件中的路径、由路径生成的头文件保护名和构建时间。记录见结果目录的 `build_command_comparison.json`、`compiled_input_comparison.json` 和 `generated_input_comparison.json`。

取舍：保留已有组内采样实现为CPU主线候选，pipeline保持默认关闭。下一步应先对重构版本增加的未覆盖成本做分项定位，再决定是否继续改变调度结构；现阶段八核局部阶段收益不足以支持替换默认实现。

# 并行前驱修复与 lookahead 确认

本轮按“并行前驱状态 → elliptic 质量 → GEMM lookahead”的顺序执行。结果保存在 `results/native_repair_20261031/`；主目标与资源比较口径沿用 [联合优化目标](native_joint_objective.md)。

## 前驱状态与修复

可选的 `VPR_HYBRID_LABEL_AUDIT=<JSONL路径>` 记录连接对共享搜索标签的实时占有。诊断复现中，网络 1120 和 1473 同时写 RR 节点 207790；两者搜索框在 y=16 重叠。`dynamic_update_bounding_boxes` 的输出网络列表按值传递，导致框已经扩张，调用者和并行分区树却没有收到更新。将输出改为引用，并在任务开始时检查网络框属于当前分区。

仅修复这一处后，检查在第 51 轮发现第二条漏通知路径：拥塞模式调用 `load_route_bb` 重载所有框，发生在原先的分区更新之后。现在两种框更新都完成后才通知分区树；全量重载通知所有网络。失败运行、诊断原始字节和 core 均保留。该复现证明了具体的并发干扰来源，但不能倒推旧 core 中每一步写入；旧 native CPU 的 SIGKILL 原因仍未确定。

路由树回溯增加无效边、越界、边终点与循环链检查。标签审计默认关闭；它需要额外同步，会改变调度，诊断计时不参与性能结论。原有 GPU 所有权保护继续保留。

## lookahead 改动

`VPR_HYBRID_LOOKAHEAD_REPORT=<JSONL路径>` 分别记录采样选择、搜索状态初始化、Dijkstra 搜索、合并及整组墙钟时间。并行时搜索与初始化为工作线程累计时间，不能直接当成墙钟时间。

GEMM 的本机分项诊断包含 10 组、40 次搜索：搜索约 160.783 秒，初始化约 0.241 秒。优化因此集中于独立采样的搜索，而非初始化。

设置 `VPR_HYBRID_LOOKAHEAD_PARALLEL=1` 可启用 TBB 并行采样。每个线程拥有独立搜索状态，每个采样拥有独立代价表；共享资源图只读。合并严格遵循原采样顺序，相同 delay 保留最先出现的 congestion。沿用 VPR 的线程上限和进程 CPU 亲和性，代价是增加并行搜索工作区内存。

ex5p、GEMM 的串并行 wire map 逐字节一致，路由主体哈希相同，均通过原版独立 FULL/STA；elliptic 新 lookahead 也复现修复后的 CPU 路由。此项等价性验证与性能测量分开。该开关默认关闭，接管阈值、批量窗口、CUDA kernel 和保护范围没有调整。

## 最终同节点确认

入口 `scripts/run_native_lookahead_confirmation.py` 使用冻结的源码、二进制和输入。所有求解及 GPU 服务线程共用相同四个物理核，额外使用一张 H100；独立回验也限制在该四核集合。CPU 亲和性与内存每五秒采样，采样峰值只是观测下界，cgroup 内存事件覆盖整个作业。

1. 构建 CUDA 库并执行回放 oracle。
2. elliptic 同轮原版串行作为质量参考，运行修复后 guard 和 batch；质量合格再补两次 batch。原版并行曾崩溃，因此此处不计算相对原版并行的加速比。
3. GEMM 对原版四线程与联合 batch 做三轮交替顺序比较，再补一次改进 CPU 控制用于归因。
4. 每项均执行锁定原版 VPR 的独立 FULL/STA。归档结束后重新核对路由、输入、实际 CUDA 库、冻结文件与 CPU 约束。

原版不启用新 lookahead，所有候选启用；双方均重新构建 lookahead，不读取缓存。所有输入同等预读，不宣称文件系统冷缓存。正式测量关闭重型诊断、CUDA events、状态捕获和 CPU 重放。

主验收仍是质量合格且 batch 三轮进程时间和含统一回验的 workflow 均优于同轮原版四线程。CPU 控制用于解释收益，不要求 GPU 必须再胜过改进 CPU；单次 CPU 控制也不能代替三轮重复证据。三个样本只支持本电路、当前机器与输入条件下的重复结果，不宣称统计显著性或跨电路泛化。计时边界见 [四核确认说明](native_joint_confirmation.md)。

首次最终确认在启动归档预留时遇到磁盘配额错误，未启动求解，零样本。对已结束生成包逐文件校验后迁移，并对相同不可变文件硬链接去重；1 GiB 预留探测成功后，以完全相同冻结包和实验配置重新提交。两个尝试和迁移记录均保留。

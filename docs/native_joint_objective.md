## 以下是本轮确认之前的目标讨论（历史状态）

主目标是：在路由合法、零超用、独立 FULL/STA 通过，且关键路径和线长退化各不超过 5% 的条件下，使我们的 CPU–GPU 联合方案端到端优于相同 CPU 核预算下的原 VPR 并行实现，并明确报告额外 GPU 配置。CPU 算法、数据结构、并行调度、任务划分和 GPU 搜索及协作的收益都属于联合方案的有效收益。

理想结果为 `T_joint < T_improved_cpu < T_original_parallel`：先证明 CPU 侧改进，再证明 GPU 带来额外收益。可接受目标为 `T_joint < T_original_parallel`；不把 GPU 必须进一步优于我们改进后的 CPU 设为联合方案有效性的必要条件。仍应如实报告纯 CPU 与联合方案的比较，帮助选择实际最优配置。

此前“四线程 CPU 贡献尚未隔离，所以不能把 batch 作为 GPU 加速证据”应限定为：暂不能归因到 GPU 的独立增益。它不能用来否定联合方案相对原 VPR 的整体收益，也不应把研究限制成只优化 GPU kernel。

## 已有 GEMM 结果的正确解释

主诊断作业内，原 VPR 单线程进程为 349.626 秒，四 CPU 工作线程加 GPU 的 batch 为 318.183 秒，观测时间短约 8.99%；含统一独立回验的 workflow 为 501.989 与 472.605 秒，观测时间短约 5.85%。batch 实际提交了 118 次 GPU 结果，FULL/STA 通过，CPD 不变、线长增加约 0.0379%。

这说明联合方案在该次测量中比原版单线程更快，但 CPU 线程数不同。尚缺本轮同 CPU 预算的原版并行对照，以及关闭诊断后的重复端到端确认；因此不能宣布已经超过原 VPR 已有的并行能力。这与是否证明 GPU 独立贡献是两个问题。旧计时、失败和验收记录保持原样。

已核实，锁定原 VPR 的 `ParallelNetlistRouter` 自带分区树和 TBB 网络级并行，支持 `--router_algorithm parallel --num_workers 4`，此前已成功运行。当前 batch 复用此框架，不能把启用四线程算作新的 CPU 并行算法贡献。新增工作是 GPU 真实状态接管、服务与组批、状态同步及所有权保护；后续更细任务发布或负载均衡若取得收益，才是新的 CPU 调度改进。

历史同一作业 `20261028-002456` 的 GEMM 进程耗时为：原版单线程 401.353 秒、原版四线程 356.545 秒、我们的 CPU 四线程控制 355.845 秒、当时 batch 362.105 秒，均合法。这轮 batch 比原版单线程快，但没有胜过原版四线程。它属于旧版本与旧测量条件，不能拿其 356.545 秒直接与新作业的 318.183 秒计算收益。

主对照采用相同 CPU 核预算的原版并行实现；单线程保留为补充缩放参考。这里的“四 CPU”实际是四个路由工作线程，不是四颗 CPU；需要记录 CPU 配额/亲和性，GPU 服务线程也计入总 CPU 预算。无需要求每一项局部改动或每个 GPU 查询单独获胜。

## 调整后的执行顺序

1. 优先做 GEMM 联合方案的正式候选确认：关闭 CUDA 诊断 events、捕获及 CPU 重复回放，同节点固定输入及 CPU 核预算，对原 VPR 并行实现和联合方案至少做三次完整流程比较，报告所有重复的进程与统一回验 workflow 时间及质量。
2. 同轮包含我们的 CPU/guard 控制，用于归因和选型；原版单线程作为补充参考。以联合方案相对原版并行基线的完整收益验收；CPU/GPU 贡献拆分不另设 GPU 独立获胜门槛。
3. 按全流程成本选择优化位置。CPU 调度、受保护的任务发布、数据处理及 lookahead 与 GPU kernel 均在范围内；GPU 内部诊断是其中一项。任何预处理或缓存策略都要明确冷启动成本、复用条件及摊销方式。
4. elliptic 先解决 batch 的完整路由收敛问题，再计算有效收益；其快照仍可用于 kernel 优化。保留所有权保护，避免局部搜索通过而完整路由不合法。

没有足够数据证明 CPU 算法已经优于原版；这正是 CPU 对照要回答的问题。当前保留 CPU 默认是部署状态，不是研究目标收缩。
